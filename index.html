(2) 다중 테이블 처리 중 정합성 깨짐 — 정산 처리 과정에서 4개 테이블에 데이터를 순차적으로 INSERT하는 구조였으나, 일부 테이블 처리 실패 시 이미 처리된 테이블의 데이터가 그대로 남아 금액 불일치가 주당 약 10건 이상 발생했고, 정산팀의 문의 메일이 반복적으로 인입되었습니다.

  • 운영 부서가 개발팀 인입 없이 직접 정책 변경 가능한 자립 구조로 전환

문제

API 시스템에서 다음과 같은 구조적 문제가 누적되어 있었습니다.

(1) 통신망별 개별 프로젝트로 운영 — 3개 통신망에 대해 각각 별도 프로젝트로 분리 운영하고 있었으나, 내부 처리 로직과 DB 구조는 대부분 동일하고 API 요청 방식·전문 내용 등 일부만 통신망별로 달랐습니다. 동일한 로직이 각 프로젝트에 중복 구현되어 있었고, 서비스 종료된 통신망의 프로젝트도 정리되지 않은 채 그대로 남아 운영 부담이 가중되었습니다.

(2) 운영 일관성 부재 — 프로젝트별로 작성자가 달랐기 때문에 에러 알림 위치, 로깅 형식, 오류 처리 방식이 모두 상이했고, 장애 발생 시 통신망별로 각기 다른 프로젝트를 확인해야 하는 비효율이 있었습니다.

해결 과정

통신망 간 공통점과 차이점을 분석한 결과, API 요청 방식과 전문 내용을 제외하면 대부분의 처리 로직이 동일함을 확인했습니다. 이에 신규 통신망마다 유사 프로젝트를 반복 생성하는 구조 대신, 공통 처리를 추상화한 통합 프로젝트로 재구성했습니다.

  • 공통 처리 로직(오류 처리·로깅 등)을 모든 구현체에 적용하기 위해 인터페이스 대신 추상 클래스를 선택, 통신망 공통 동작을 추상 메서드로 정의
  • 통신망별 구현체에서 API 요청 방식·전문 내용 등 차이를 처리
  • 가맹점·거래 정보에 매핑된 통신망 코드를 기준으로 적절한 구현체를 라우팅
  • 통신망별 타임아웃·재시도 정책 등 운영 정책 값은 DB로 분리 관리하여, 배포 없이 운영 중 조정이 가능하도록 설계
결과
  • 3개 통신망별 개별 프로젝트로 분산되어 있던 구조를 1개 통합 프로젝트로 일원화. 운영 안정성을 고려해 기존 프로젝트는 유지하면서 신규 거래는 통합 프로젝트로 처리하는 점진적 전환 방식으로 진행
  • 프로젝트 진행 중 신규 통신망 2개 연동 요청이 들어왔으며, 구현체 추가만으로 확장 가능함을 실제로 검증
  • 장애 발생 시 다수 프로젝트를 각각 확인하던 구조에서 단일 프로젝트 확인으로 일원화, 신규 입사자 및 타 팀 인수인계 효율 향상

📌 개요

PDF·DOCX 문서와 YouTube 영상을 AI로 분석·비교하는 SaaS 플랫폼. 구독 서비스·팀 관리까지 포함한 사이드 프로젝트.

문제

로컬 환경에서는 정상 동작하던 youtube-transcript 라이브러리가 Vercel 배포 환경에서는 자막 추출에 실패하는 현상 발생. 원인 분석 결과, YouTube가 Vercel IP를 봇 트래픽으로 감지해 차단하기 때문에 라이브러리 버전 문제가 아닌 YouTube의 정책 구조적 이슈로 확인.

해결 과정

Vercel IP 차단을 우회하기 위해 라이브러리 교체 → 클라이언트 사이드 호출 → Edge Runtime + ANDROID 클라이언트 위장까지 다섯 차례 시도했으나 안정성 확보 실패. 최종적으로 외부 API(Supadata)로 위임하여 코드량을 50% 이상 줄이고 실패율을 0에 수렴시킴.

결과

자막 추출 안정화 및 코드 복잡도 대폭 감소. 우회 시도 중 만든 사전 자막 체크 UI, 자막 분석 API 입력 구조 변경 등은 최종 구조에서도 유효해 그대로 유지. 코어 비즈니스(분석)가 아닌 영역은 외부 위임이 합리적이라는 Build vs Buy 판단 기준을 직접 검증.

📌 개요

TMDB·KOBIS·Gemini API를 연동한 OTT 콘텐츠 통합 탐색·평가 플랫폼. Spring Security 기반 Form 로그인 + Google/Kakao OAuth2 통합 적용.

문제

TMDB는 약 50만+ 콘텐츠를 보유하고 있어 전량 미러링 시 DB 비용·저작권·동기화 부담이 컸고, 반대로 매 요청마다 외부 API를 호출하는 방식은 rate limit과 응답 지연 이슈가 발생.

해결 과정

전량 미러링 vs 매번 호출 사이에서 사용자 트래픽 패턴에 맞춘 Sync-on-demand 전략을 채택했습니다. 상세 페이지에 최초 접근하는 시점에만 TMDB API를 호출해 DB에 적재하고, 이후 동일 콘텐츠 조회는 DB에서 응답하는 방식입니다. 또한 관리자 페이지에서 키워드 검색 기반 단건 동기화 기능을 보강해 운영 대응성도 확보했습니다.

결과

초기 DB 부담 없이 점진적 데이터 적재 가능. 사용자 실제 조회 패턴에 맞게 데이터가 누적되어 인기 콘텐츠는 캐시처럼 빠르게 응답하는 구조 확보.
